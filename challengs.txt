Technical Challenges in Building a Global User Profile Page (Interview Discussion Points)

1. Data Synchronization (Auth vs. Database):
   - Challenge: Supabase manages authentication (emails, sessions) while MongoDB stores application data.
   - Solution: Creating a seamless sync mechanism where a MongoDB User document is created/updated instantly via API routes when a user sets up their profile.
   - Architectural Decision Note: Why MongoDB instead of Supabase Postgres? Since all core application data (Resources, Comments) is stored in MongoDB, storing User Profiles in Supabase would require complex, slow cross-database joins (e.g., fetching a resource from MongoDB and then making a separate API call to Supabase for the author's bio/badge). Keeping the User model in MongoDB allows for fast `populate()` queries and efficient aggregation pipelines.

2. Dynamic SEO & Server-Side Rendering (SSR):
   - Challenge: Each profile needs unique SEO tags (OpenGraph images, titles) so when shared on Twitter/LinkedIn, the preview looks correct.
   - Solution: Using Next.js generateMetadata to fetch user data server-side before the page loads, and generating dynamic OG images for each user.

3. Username Uniqueness & Routing Conflicts:
   - Challenge: Implementing clean URLs like /user/johndoe requires ensuring usernames are globally unique and don't clash with reserved application routes (e.g., /user/settings).
   - Solution: Writing strict regex validation and maintaining a blacklist of reserved keywords during onboarding.

4. Data Privacy & Access Control:
   - Challenge: The profile API must fetch user data, but sensitive fields (like private emails) must never be exposed to the public frontend.
   - Solution: Implementing strict projection queries in MongoDB (e.g., .select('-email')) and verifying auth tokens for showing edit permissions.

5. Aggregation Performance & Caching (Scalability):
   - Challenge: A global profile might need to show total views and upvotes across all their resources. Running heavy DB queries per visit is slow.
   - Solution: Using MongoDB Aggregation Pipelines to efficiently calculate total impact, and caching the page using Next.js ISR (Incremental Static Regeneration).

6. Cold Start Seeding & Fake Accounts (Growth Hack):
   - Challenge: A new platform looks empty. We needed to post high-quality resources without creating dozens of real Supabase accounts with emails/passwords.
   - Solution (Admin Override Logic & Debugging):
     1. We created a Node script (`seedUsers.mjs`) to inject dummy `User` profiles (e.g. "Rahul Sharma") directly into MongoDB, bypassing Supabase auth entirely.
     2. In the "Create Resource" frontend (`app/dashboard/write/page.tsx`), we built a hidden dropdown that only renders if the logged-in user matches `process.env.NEXT_PUBLIC_SUPERADMIN_EMAILS`.
     3. When the Admin selects a fake alias (e.g., "Rahul Sharma") and submits the form, the frontend passes `overrideAuthorId` in the API payload.
     4. I manually debugged the backend logic (`/api/documents/[id]/route.ts`) to intercept this payload. I wrote the logic to fetch the fake user from DB, override `userId`, `authorName`, `isVerified`, etc. in the request body, and delete `overrideAuthorId` so it saves the resource perfectly on behalf of the alias!

7. Hybrid Global Clock:
   - Challenge: Running `setInterval` on individual contest cards for countdowns causes severe performance issues (re-rendering many components simultaneously every second) and introduces hydration mismatches between Server-Side Rendering (SSR) and Client-Side Rendering (CSR). Furthermore, if the user's system clock is out of sync, individual countdown calculations might differ or break.
   - Solution: Implemented a **Hybrid Global Clock Architecture**.
     - Global Clock Singleton: A single `useGlobalClock` hook acts as a central event emitter. It runs exactly ONE `setInterval` (1-second tick) for the entire application, passing the current UTC timestamp to any subscribing component.
     - Hydration Safety: The clock initializes as `null` on the server and sets itself to `Date.now()` upon client hydration. This guarantees zero SSR hydration mismatches.
     - Smart Refresh / Adaptive Precision: Instead of ticking every second, countdown strings are dynamically formatted based on proximity (> 24h, > 1h, < 1h, Live).
     - Centralized Logic: `DsaContestCard.tsx` consumes the singleton clock to compute its string, falling back to a static render if the clock hasn't hydrated yet.

8. Selective Googlebot API Access in robots.ts:
   - Challenge: Google Search Console reported `Page resources 1/32 couldn't be loaded - Googlebot blocked by robots.txt` for XHR requests to `https://contest-tracker-zms3.vercel.app/api/contests` when rendering public pages like `/contests`. Because `robots.ts` previously disallowed all `/api` and `/api/` paths universally, Googlebot refused to execute client-side XHR fetches during page rendering.
   - Solution: Configured path-specific `allow` rules in `app/robots.ts` for public data endpoints required during page rendering (`/api/contests`, `/api/resources`).
     - Standard Googlebot robots.txt parsing evaluates the longest (most specific) matching prefix rule.
     - `Allow: /api/contests` (length 13) takes precedence over `Disallow: /api/` (length 5) for contest fetches.
     - Private endpoints (`/api/admin`, `/api/cron`, `/api/user`, etc.) remain disallowed and protected from crawler indexing.

9. Client-Side Rendering (CSR) Blank Loading & SEO Crawlability:
   - Challenge: Fetching contest and resource data inside `useEffect` (CSR) caused a blank "Loading..." screen during initial page load, degrading user experience. Furthermore, search engine crawlers often fail to index dynamic content that is fetched asynchronously after the initial HTML shell is loaded, severely impacting SEO and social sharing metadata.
   - Solution: Refactored complex, state-heavy pages (`/contests` and `/resources/[id]`) to a Next.js App Router Server-Side Rendering (SSR) architecture.
     - Server Components (`page.tsx`) now execute the heavy data fetching directly (connecting to MongoDB or invoking web scraping logic) before HTML generation.
     - Fetched data is passed down as `initialData` props to Client Components (`ContestBoardClient.tsx`, `ResourceClient.tsx`), which handle all local UI interactivity (e.g., active Javascript countdown timers, upvoting, filters).
     - By injecting dynamic metadata via `generateMetadata` in the Server Component and shipping pre-populated HTML to the client, we eliminated the blank loading screen entirely and guaranteed perfect crawler indexing without sacrificing rich client-side features.

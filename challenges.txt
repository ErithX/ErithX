# Architecture Decision: Hybrid Global Clock
Date: 2026-07-22

## Problem
Running `setInterval` on individual contest cards for countdowns causes severe performance issues (re-rendering many components simultaneously every second) and introduces hydration mismatches between Server-Side Rendering (SSR) and Client-Side Rendering (CSR). Furthermore, if the user's system clock is out of sync, individual countdown calculations might differ or break.

## Solution
Implemented a **Hybrid Global Clock Architecture**.
- **Global Clock Singleton:** A single `useGlobalClock` hook acts as a central event emitter. It runs exactly ONE `setInterval` (1-second tick) for the entire application, passing the current UTC timestamp to any subscribing component.
- **Hydration Safety:** The clock initializes as `null` on the server and sets itself to `Date.now()` upon client hydration. This guarantees zero SSR hydration mismatches.
- **Smart Refresh / Adaptive Precision:** Instead of ticking every second, countdown strings are dynamically formatted based on proximity:
  - > 24 hours: "Starts in 4d 12h"
  - > 1 hour: "Starts in 12h 45m"
  - < 1 hour (Imminent): "Starts in 45m 12s" (Second-level precision only used when necessary).
  - Live: "Ends in HH:MM:SS"
- **Centralized Logic:** `DsaContestCard.tsx` consumes the singleton clock to compute its string, falling back to a static render (Date/Time) if the clock hasn't hydrated yet.

This ensures scalability for 100+ cards without tanking browser performance.
